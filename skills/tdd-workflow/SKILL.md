## 纪律总纲（Evidence over Claims）

1. **每一步必须有真实证据**：测试输出、命令退出码、覆盖率数字——而不是"应该没问题"
2. **先看测试失败，再写实现**：没见过 RED 的测试不可信
3. **最小实现**：只写让测试通过所需的最少代码
4. **实现先于测试编写的代码应删除重来**

## Phase 1: RED — 写失败的测试 🔴

### 1.1 分析需求
- 识别主要功能与输入/输出
- 列出边界条件与错误场景
- 定义验收标准

### 1.2 设计测试策略
- 简单功能：单元测试 + happy path 优先
- 中等复杂度：补集成测试与错误处理
- 复杂功能：加 e2e 与性能基线

### 1.3 编写并**运行**测试
```bash
npm test -- --watch  # 或对应框架命令
```
**必须确认测试失败**，并记录失败信息（这是 RED 证据）。

## Phase 2: GREEN — 最小实现 🟢

- 只写让失败测试通过所需的代码
- 不做提前优化、不加未要求的功能
- **运行测试确认全部通过**（GREEN 证据）
- 提交：`git commit -m "feat: ... (RED->GREEN)"`

## Phase 3: REFACTOR — 重构 ♻️

- 消除重复、提升可读性，**不改变行为**
- 每次重构后**重新运行测试**确认仍绿
- 重构中测试变红 = 立即停下修复或回滚

## 常见反模式（禁止）

| 反模式 | 正确做法 |
|--------|---------|
| 测试和实现一起写 | 先写测试看它失败 |
| 实现写完再补测试 | 删掉实现，从 RED 开始 |
| 断言写死返回值不看真实输出 | 先跑起来观察实际行为 |
| "测试通过了"但没贴输出 | 展示命令输出与退出码 |

## 下一循环

回到 Phase 1 处理下一个最小增量。保持每轮 2-5 分钟粒度。
